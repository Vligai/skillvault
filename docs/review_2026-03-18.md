# SkillVault Project Review — 2026-03-18

## Executive Summary

SkillVault is a well-engineered, security-first CLI tool that distributes AI agent skill prompts across 14 AI coding platforms. Its zero-dependency design, comprehensive test suite, and clear separation of concerns make it a solid foundation. This review covers architecture, security, and usability, with prioritized recommendations for improvement.

---

## 1. Architecture

### 1.1 Overview

```
skillvault/
├── bin/cli.js          # Entry point: arg parsing, interactive UI, orchestration
├── lib/installer.js    # Core logic: platform/skill registry, file operations
├── test/cli.test.js    # Test suite: 50+ cases, zero external dependencies
├── skills/claude/      # 10 skill prompt files (developer, security, cloud, user)
├── .claude/commands/   # Claude-specific thin wrapper files
├── docs/               # Guardrails template + roadmap
└── .github/workflows/  # CI matrix: Node 18/20/22
```

**What it does:** `npx skillvault init` detects which AI coding tool is present in the user's project, then copies security skill prompts and guardrails to the correct platform-specific directories.

### 1.2 Strengths

- **Excellent separation of concerns.** CLI logic lives in `bin/cli.js`; all installation logic is in `lib/installer.js`. This makes each module independently testable and readable.
- **Zero production dependencies.** The entire tool runs on Node.js built-ins (`fs`, `path`, `readline`). This is a deliberate, correct architectural decision that eliminates supply-chain risk entirely.
- **Idempotent operations.** Running `init` multiple times is safe; existing files are overwritten and guardrails are not duplicated if already present.
- **Registry-driven design.** `SKILLS` and `PLATFORMS` constants serve as the single source of truth. Adding a new skill or platform requires only adding an entry to these arrays plus the content file.
- **Dry-run mode.** Users can preview all changes before they are written to disk.

### 1.3 Concerns

#### High Priority

**C1 — Monolithic CLI file (650 lines)**
`bin/cli.js` handles argument parsing, interactive prompts, platform detection, summary rendering, and config I/O. As the platform count grows toward the 40+ skill roadmap, this will become a maintainability burden.

*Recommendation:* Extract into sub-modules: `lib/args.js`, `lib/prompt.js`, `lib/config.js`, `lib/reporter.js`.

**C2 — No config schema version**
`.skillvaultrc` has no `version` field. When the schema changes (e.g., adding `severity` or `category` fields from the roadmap), there is no migration path and old configs will silently behave unexpectedly.

*Recommendation:* Add `"version": 1` to `.skillvaultrc` and validate it on read. Emit a warning when the version is absent or outdated.

#### Medium Priority

**C3 — Platform registry is split across two files**
Platform metadata is defined in `lib/installer.js` but some platform-specific behaviour (e.g., guardrails header injection) is scattered in `bin/cli.js`. A user adding a new platform must touch both files.

*Recommendation:* Consolidate all per-platform metadata (slug, dir, type, guardrails header) into `lib/installer.js` as a single `PLATFORMS` map.

**C4 — `remove` command leaves empty directories**
When all skills are removed from a platform, the skill directory (e.g., `.claude/commands/`) is left empty. This can confuse users or future detection logic.

*Recommendation:* After removing the last skill from a directory, attempt `rmdirSync` with a check that the directory is empty.

#### Low Priority

**C5 — No TypeScript or JSDoc types**
The codebase is plain JavaScript with no type annotations. Public function signatures (especially in `installer.js`) would benefit from JSDoc for IDE support.

**C6 — `update` command re-copies all skills without version awareness**
There is no concept of skill versions. `update` always overwrites with whatever is in `node_modules/skillvault/skills/`. If a user has customized a skill file, the change is silently lost.

*Recommendation:* Before overwriting, checksum the installed file against the package source. Warn the user if the file has been locally modified and prompt before overwriting.

## 2. Security

### 2.1 Security Posture: Strong

This is a security-tooling project that practices what it preaches. No critical vulnerabilities were found.

### 2.2 Strengths

| Control | Implementation | Assessment |
|---|---|---|
| No hardcoded secrets | Confirmed — none present | Pass |
| Input validation | Skill slugs and platform keys are whitelisted against `SKILLS`/`PLATFORMS` | Pass |
| Safe path construction | All paths built with `path.join()` | Pass |
| Zero external dependencies | Runtime: 0 npm packages | Pass |
| Config validation | `.skillvaultrc` parsed with JSON.parse + field-level checks | Pass |
| No shell execution | No `exec`/`spawn`; pure Node.js fs operations | Pass |
| Dry-run support | Full preview without writes | Pass |
| Error messages | Do not leak sensitive internals | Pass |

### 2.3 Issues Found

#### Medium Priority

**S1 — No integrity check on installed skill files**
When `npx skillvault init` runs, it copies files from the npm package into the user's project. There is no checksum or signature verification. A compromised npm package would silently install malicious skill content into developer environments.

*Recommendation:* Publish SHA-256 checksums of each skill file in a `checksums.json` (included in the npm package and published to a known URL). The CLI should verify files against `checksums.json` before writing them. This is especially important since the installed files become part of AI agent context that influences code generation.

**S2 — `guardrails.md` appended without idempotency check on content hash**
The code checks for the presence of a marker string to avoid duplicating guardrails, but does not detect if the existing guardrails are from an older version of the package. A user who has installed then updated the package may have stale guardrails with no indication.

*Recommendation:* Embed a version comment (e.g., `<!-- skillvault-guardrails v1.2 -->`) in the injected block. On `update`, detect the old version tag and replace the block instead of appending.

#### Low Priority

**S3 — No file permission enforcement**
`fs.copyFileSync()` and `fs.mkdirSync()` use default system umask. On shared systems or in CI environments with permissive umasks, installed skill files could be world-readable or world-writable.

*Recommendation:* Pass explicit mode to `mkdirSync` (`0o755`) and set file mode `0o644` after copy via `fs.chmodSync()`.

**S4 — JSON config depth not bounded**
`JSON.parse()` on `.skillvaultrc` is safe against stack overflow in all maintained Node.js versions, but the `validateConfig()` function does not enforce a maximum nesting depth on user-supplied arrays. For correctness (not security), add a guard that emits a clear error if `skills` is not a flat string array.

**S5 — No `.npmignore` / `files` audit for sensitive content**
`package.json` uses `"files"` to restrict what's published. The `skills/`, `bin/`, and `lib/` directories are included. The `docs/ideation.md` roadmap is also published (it's in `docs/`). This is not a vulnerability but may expose internal planning detail prematurely.

*Recommendation:* Explicitly exclude `docs/ideation.md` from the published package or move it to `.github/` where it reads as clearly internal.

### 2.4 Supply Chain Notes

Because SkillVault skill files are injected into AI agent context (e.g., `CLAUDE.md`, `.cursor/rules/`), a compromised or malicious skill file could subtly influence code generation in the user's project. This is a higher-than-typical supply-chain impact surface. The zero-dependency design is the strongest mitigation already in place; the integrity check recommendation (S1) would complete this layer.

## 3. Usability

### 3.1 CLI Experience

The CLI provides a clean, interactive experience suitable for developer audiences. The use of `readline` for interactive selection, combined with JSON output mode (`--json`) for scripting, covers both human and automated use cases well.

### 3.2 Strengths

- **Good discoverability.** `npx skillvault list` shows what's installed vs. available with clear status indicators.
- **`doctor` command.** Shows version, detected platforms, and installed skill count — helpful for support and debugging.
- **`--dry-run`** lets users audit changes before committing.
- **`--save` + `.skillvaultrc`** enables reproducible installs across team members.
- **`--category` filter** allows partial installs by developer/security/cloud/user persona.

### 3.3 Issues Found

#### High Priority

**U1 — No confirmation prompt before destructive operations**
`skillvault remove --all` deletes all installed skills with no confirmation prompt. A typo or mis-paste can silently destroy customized skill configurations.

*Recommendation:* Require explicit confirmation (`Are you sure? [y/N]`) for `remove --all` unless `--force` or a non-TTY environment is detected (for CI use).

**U2 — `update` gives no feedback when nothing changes**
If all skills are already at the latest version, `update` completes silently. Users cannot tell whether the update did anything.

*Recommendation:* Always print a summary: "3 skills already up to date, 0 updated."

#### Medium Priority

**U3 — Platform detection order is implicit**
When multiple platforms are detected (e.g., Claude Code and Cursor both present), the CLI prompts the user to choose — but the detection order and tie-breaking logic are not documented. Users working across multiple AI tools need to run `init` multiple times, once per platform.

*Recommendation:* Allow `--platform claude,cursor` as a comma-separated flag for multi-platform installs in a single command. Also document detection priority in `README.md`.

**U4 — Error messages on unknown flags go to stderr but don't terminate**
Unknown CLI flags produce a warning but the command continues. This can mask user mistakes (e.g., `--catagory` instead of `--category`).

*Recommendation:* Treat unknown flags as fatal errors (exit 1) with a message pointing to `--help`.

**U5 — No `--help` or `-h` flag**
The CLI has no built-in help output. New users must consult the README.

*Recommendation:* Implement `skillvault --help` and `skillvault <command> --help` with usage, flags, and examples.

#### Low Priority

**U6 — Interactive prompt has no default selections**
When the skill selection prompt appears, no skills are pre-selected. For new users, the guidance on which skills to start with is only in the README.

*Recommendation:* Pre-select a curated "starter pack" (e.g., `review`, `scan-secrets`, `audit-deps`) and let users deselect unwanted skills.

**U7 — JSON output (`--json`) is not consistent across commands**
`list --json` produces structured JSON, but `init --json` and `update --json` output is not documented as machine-readable. For CI integration, all commands should support `--json` with a consistent schema.

**U8 — No changelog or migration guide**
There is no `CHANGELOG.md`. When users run `update`, they have no way to know what changed between skill versions.

*Recommendation:* Maintain a `CHANGELOG.md` and link to it from the README's "Updating" section.

## 4. Testing

### 4.1 Assessment: Good

- 50+ test cases using Node.js built-in test runner — no external framework needed.
- Tests cover platform detection, file installation, config parsing, dry-run mode, and edge cases.
- CI runs against Node 18, 20, and 22 on `ubuntu-latest`.

### 4.2 Gaps

**T1 — No test for `remove` command**
The `remove` command has no test coverage. This is a destructive operation and should be tested for both partial (`--skill`) and full (`--all`) removal.

**T2 — No test for `update` behavior when a file has been locally modified**
Once recommendation C6 is implemented, this needs a test to verify the checksum comparison and prompt logic.

**T3 — CI runs on Linux only**
The tool installs files on macOS and Windows as well, but CI only runs on `ubuntu-latest`. Windows path handling (`path.join` on `win32`) is untested.

*Recommendation:* Add `windows-latest` and `macos-latest` to the CI matrix.

**T4 — No integration test via `npx`**
All tests invoke the modules directly. There is no end-to-end test that runs `npx skillvault init` from a fresh install, verifying the published package shape.
